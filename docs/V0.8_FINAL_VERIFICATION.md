## 4. Ingestion Scheduler

The `IngestionScheduler` runs continuously inside the FastAPI application lifespan (`backend/app/main.py`).

### Key Capabilities Verified
1. **FastAPI Lifespan Startup & Shutdown**: Initializes at application startup and terminates gracefully on SIGINT/SIGTERM with tasks drained.
2. **Independent Source Scheduling**: Each source checks its own `polling_interval_seconds` relative to its `last_attempted_fetch_at`.
3. **No Frontend Polling Dependency**: The scheduler operates entirely server-side regardless of whether client dashboards are open or closed.
4. **Overlap Prevention**: Managed via in-memory `_running_sources: set[UUID]`. A source currently undergoing fetch is skipped during scheduler ticks without penalty.
5. **Bounded Exponential Backoff**: Failures increment `consecutive_failures`, delaying the next retry by `min(3600.0, 1.5 ** failures)` seconds.
6. **Uptime & Status Telemetry**: Runtime state exposed via `GET /api/v1/ingestion/status`.

## 6. Freshness Model

Explicit, deterministic, timestamp-based freshness semantics prevent conflation of publication time, insertion time, and client render time.

### Configurable Thresholds (`backend/app/config/settings.py`)
- `FRESHNESS_CURRENT_HOURS = 24.0` (Events within 24h of publication)
- `FRESHNESS_RECENT_DAYS = 7.0` (Events within 7 days of publication)
- `FRESHNESS_STALE_DAYS = 30.0` (Events > 7 days up to 30 days)
- `SOURCE_STALE_MULTIPLIER = 2.0` (Source is STALE if elapsed time > 2x polling interval)

### Freshness States
1. **Source Freshness**:
   - `FRESH`: `elapsed_seconds <= polling_interval_seconds * 1.5`
   - `RECENT`: `elapsed_seconds <= polling_interval_seconds * 2.5`
   - `STALE`: `elapsed_seconds > polling_interval_seconds * 2.5`
   - `UNKNOWN`: No successful fetch on record.
2. **Document & Event Freshness**:
   - `FRESH`: `(now - published_at) <= 24 hours`
   - `RECENT`: `(now - published_at) <= 7 days`
   - `STALE`: `(now - published_at) > 7 days`
   - `UNKNOWN`: `published_at` is null.

*Rule: Historical articles ingested today are explicitly classified by their original `published_at` timestamp, NEVER labeled "FRESH" simply because they were newly added to the database.*

## 7. Continuous Processing Pipeline

The document pipeline implements a formal state machine:
```
RAW  ──▶  NORMALIZED  ──▶  EXTRACTION_PENDING  ──▶  EXTRACTED  (or FAILED)
```

### State Transitions & Idempotency
- Newly ingested documents start at `RAW` and proceed through normalization and event/entity extraction.
- **Idempotency Guard**: If `document.processing_status == "EXTRACTED"` and `reprocess=False`, the pipeline returns `SKIPPED_ALREADY_EXTRACTED` immediately. No duplicate events, entities, or clusters can be created by re-running the pipeline.
- **Backlog Tracking**: Unprocessed documents (`RAW`, `NORMALIZED`, `EXTRACTION_PENDING`) are tracked via `get_ingestion_backlog(db)`. In production, the current backlog queue depth is **0**.

## 10. Deterministic Alerts

Alerts are produced strictly from deterministic rule triggers (`backend/app/services/alert_service.py`):
1. `HIGH_IMPORTANCE_EVENT`: Triggered when extracted event importance >= 0.80.
2. `MAJOR_ECONOMIC_RELEASE`: Triggered when an economic observation exceeds significance thresholds.
3. `DATA_QUALITY_FAILURE` / `SOURCE_STALE`: Triggered when consecutive failures >= 3 or elapsed fetch time exceeds stale thresholds.
4. `PROCESSING_BACKLOG_EXCEEDED`: Triggered when pending unprocessed documents exceed threshold (default: 50).
5. `HIGH_INGESTION_FAILURE_RATE`: Triggered when recent runs fail at a rate > 50%.
6. `SIGNIFICANT_CLUSTER_UPDATE`: Triggered when an event cluster reaches >= 3 corroborated member events with confidence >= 0.80.

*Strict Non-Causal Boundary: Alerts contain evidence IDs and factual descriptions. They never forecast price movements, recommend trades, or infer market causality.*

10. Missing publication timestamp -> Assigned `None`, freshness set to `UNKNOWN`.
11. Processing failure during extraction -> Document marked `FAILED`, other documents continue.
12. Scheduler restart -> Resumes scheduling cleanly without dropping source states.
13. Application restart -> Ingestion runs and document states preserved in DB.
14. Overlapping scheduler execution -> Blocked by `_running_sources` lock.
15. Database unavailable -> Logs connection error and retries with backoff.
16. Partial source failure -> One failing feed does not affect other active feeds.
17. Large backlog processing -> Batch pagination prevents memory exhaustion.
18. Stale source detection -> Source status switches to `STALE` when elapsed time > threshold.
19. Missing location entity -> Displays `Location Unresolved`; no coordinates fabricated.
20. Missing event time -> Event time preserved as `None` or fallback to publication time.
21. Duplicate entity resolution -> Canonical deduplication prevents duplicate entity inserts.
22. Duplicate event prevention -> Existing document event check prevents duplicate events.
23. Alert deduplication -> Duplicate alerts within window are suppressed.
24. API pagination bounds -> Clamped limits (min 1, max 100) prevent unbounded queries.
25. Production / test DB misconfiguration -> Triggers immediate runtime assertion block.
